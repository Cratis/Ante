---
title: Diagnose onboarding
description: Locate missing invitations, failed token issuance, unpublished acceptance, and host-side delays.
---

Use the invitation's GUID event source id to trace it across host outbox, Ante inbox, Ante local event log and Ante outbox. A correlation id is separate metadata. Do not replay a command merely because the UI has waited 20 seconds.

## No invitation or token

1. Check that the host wrote `UserInvitedToJoinTenant` or `UserInvitedToCreateTenant` to its **outbox**, not just its event log, under a GUID id. If the id is not a nonempty lowercase hyphenated (`D`-format) GUID, Ante writes `InvitationRejected(InvalidInvitationId)` to its outbox under the original id and logs a warning; there will be no new local receipt or token. A revocation under that id is ignored. Ante observes one `inbox-{source}` per `Ante:HostStores` entry (default `["Direct"]`); check the source is configured, its source-name subscription has the three invitation filters (plus legal publication for the selected Inbox-mode publisher), its observer is subscribed, and the host/Ante namespaces match. A change to the source list needs a restart, not a rebuild.
2. Look for Ante's local `JoinTenantInvitationReceived` or `CreateTenantInvitationReceived` under the same id. If absent, inspect the particular source's outbox, `inbox-{source}`, and source-qualified observer state, including failed/quarantined partitions. `/healthz/ready` checks that the inbox reactor is subscribed and active, not whether source forwarding and receipt appends are healthy or caught up. A failed receipt append stops acknowledgment, so resolve its constraint/concurrency/error and let Chronicle retry rather than manually replaying another invite.
3. If the id was previously revoked or accepted, first check Ante's outbox for `InvitationRejected(InvitationIdReused)`; a different invitation under that id produces no new receipt or token. Mint a fresh GUID rather than retrying the closed id. If a receipt exists but `InvitationTokenIssued` does not appear in Ante's outbox, check `InvitationTokenIssuingReactor`'s partition errors and `PrivateKeyPem`. Rejected outbox appends throw `OutboxPublicationFailed` with constraint, concurrency or error details; the partition pauses and may be quarantined after repeated failures. Check the same failure on `IncomingInvitationReactor` when publishing an invalid-id rejection. Fix the underlying append failure and recover the partition through Chronicle's operator controls; do not claim a token was sent until you can see the outbox fact.

## Legal documents unavailable or quarantined

With `Ante:Legal:Source=Inbox`, an empty or failed legal query is **not** permission to skip consent. Before the first usable activation, `/api/legal/current` reports `isUnavailable: true`; all three onboarding commands reject with a retryable message. Check `Ante:Legal:PublisherStore` is in `Ante:HostStores`, `Ante:Legal:DocumentSetId` matches the host's outbox event-source id, both stores use the same namespace, and the host published `LegalDocumentSetPublished` to its **outbox**. Look for `LegalDocumentSetReceived` under that id in Ante's local event log and `LegalDocumentSetActivated` in Ante's outbox and the host inbox. Readiness checks the runtime observer, not whether the first legal set arrived or whether the acknowledgement was forwarded. A failed local append or outbox append must be investigated and retried through Chronicle's observer recovery, not interpreted as an activation.

A contradictory revision, reused version with different content, or invalid/empty set is recorded as local `LegalDocumentSetRejected` with `Revision`, `Version`, `InboxSequenceNumber` and a non-sensitive `Reason` (`ConflictingRevisionOrVersion` or `InvalidSet`). It does **not** quarantine Chronicle's entire inbox partition; the observer can continue receiving later valid sets. Query the local legal stream for this fact and correlate its inbox number with `inbox-{publisher}`; inspect the host's authoritative version archive. Correct the host publisher with a **new** revision and version, rather than editing historical events or reusing the rejected identity. Old out-of-order snapshots and exact duplicate deliveries produce no activation or rejection. Ante's latest activated revision remains current until a newer usable one commits. Protect access to document text and operational logs.

## Pending invitations from historical malformed receipts

Before the canonical-id check, Ante could record local receipt events under malformed invitation ids. The pending read models use `InvitationId(Guid)` as their key: an unparseable id can make the projection fail, while a parseable but noncanonical id can leave a pending MongoDB document that `collection.Observe()` cannot safely deserialize or match to its original event-source-id string. A local rejection-removal event under the malformed id would hit the same GUID key-conversion problem (or normalize to a different id), so it is **not** a reliable cleanup mechanism.

If a pending-invitations query or projection fails, inspect the local receipt events and the corresponding pending read-model documents for the affected invitation. Back up and remove **only verified malformed documents** using the deployment's approved MongoDB procedure. Resolve the offending historical receipt in Chronicle through the approved operator revision/redaction process before replaying or rebuilding the projection, or the document or partition failure may recur. Do not delete all pending invitations, replay blindly, or alter the host's valid invitation stream. The normal inbox rejection path prevents new malformed receipts but does not repair historical data.

## Recorded but not published

On releases v0.5.0 through v0.10.0 ([Ante #72](https://github.com/Cratis/Ante/issues/72)), every acceptance stays recorded but unpublished, because the forwarding reactors never ran. Upgrade as described in [Deployment](./deployment.md#upgrade-from-a-release-without-working-outbox-forwarding).

Check `UserSetupAcceptanceStatusView.StatusForInvitation` for joins or `OrganizationSetupAcceptanceStatusView.StatusForInvitation` (or `StatusForRegistration` for self-registration). If it reports `Recorded`, the acceptance/registration fact committed to Ante's **local log** but the host-facing outbox is not yet confirmed. Do **not** resubmit. Compare local and outbox records under that id: the status reaches `Accepted` only when the primary fact **and any locally recorded `LegalTermsAccepted`** have reached the outbox. Inspect `JoinTenantAcceptanceOutbox`, `OrganizationSetupOutbox`, or `OrganizationRegistrationOutbox` for the main fact and `LegalTermsAcceptanceOutbox` for consent. Look for their partition errors (`OutboxPublicationFailed` when `AppendResult.IsSuccess` is false), Chronicle connectivity and observer progress. The acceptance and legal reactors may append to the same outbox source concurrently without an expected-sequence check; a reported append failure still pauses the partition for retry. Repeated forwarding may duplicate a fact, so the host must deduplicate. No independent publication-lag readiness metric is implemented. If all four forwarding observers are disconnected just after the first start, restart Ante once as described in the upgrade instructions.

If status is `Pending`, check that the invitation was received and its pending projection caught up; do not treat a transient UI spinner as an invitation. If status is `Accepted` but the host did not provision, trace the host observer and host-side checks: Ante's accepted state reports outbox publication, **not** host success. With `Ante:HostOutcomeUrl`, the invited-flow completion screen can ask the host for an informational result, but `Unknown` can mean absent/unreachable/malformed response and does not change Ante's status. Self-service registration has no such outcome lookup.

## Operator visibility

Keep the operator view in the host console, where the host can authorize staff and scope results to its tenants. Today Ante offers `/healthz` and Mongo/inbox `/healthz/ready`, owner-scoped status queries, Chronicle inbox/event-log/outbox and observer partition state, and application logs for diagnosis; it has no consolidated operator dashboard or service diagnostics endpoint. Token publication does not mean the host sent or delivered mail. A narrow read-only, service-authenticated diagnostics API is planned in [Ante #62](https://github.com/Cratis/Ante/issues/62); do not use invitee status queries as an operator API.

## Rehearse a quiesced erasure

This is a **manual procedure to rehearse before use**, not an automated or proven complete-erasure feature. Obtain the host's approved subject mapping, retention decision and legal-hold clearance, then:

1. Stop new writes from affected host/Ante operations, drain in-flight forwarding (including host relays), then pause those forwarders before deletion. Do not allow replay or reissuance during deletion.
2. Inventory the subject's keys and plaintext/session/read-model copies in **every** affected event store and namespace, including host and Ante, and account for logs, links, exports, backups and restore paths. An invitation id need not equal the compliance subject.
3. Remove the authorized sessions and plaintext copies, then delete each affected key **through Chronicle's erasure path** in every affected store and namespace, so the erasure fence is recorded with the deletion. Do not remove key documents directly in MongoDB: that records no fence, and Chronicle 19.4.7 copies the source key back into the target on the next forwarded event.
4. Verify that each key is gone **and** that its erasure fence is present in every store and namespace (a missing key alone can pass before the next forwarded event restores it). Verify absence/inaccessibility of the other copies and a safe replay/restore path before restarting writers and forwarders. If any store is unavailable or a copy returns, do not report erasure complete; keep the operation quiesced and escalate.

See [Personal data, retention and erasure](./security.md#personal-data-retention-and-erasure) and [Ante #64](https://github.com/Cratis/Ante/issues/64). This outline does not substitute for a deployment-specific tested procedure or a verified erasure acknowledgement.

## Dependency and identity failures

`/healthz` runs no dependency checks; `/healthz/ready` pings MongoDB and checks that every configured inbox reactor is subscribed and active or replaying (three-second per-check timeout). Inspect Chronicle registration and source outbox subscriptions independently even if ready is green: reactor state does not establish source availability, correct namespace forwarding, cursor progress or host provisioning. If host inbox registration fails, Ante starts and stays live while `/healthz/ready` returns 503; background registration retries with capped exponential backoff (up to 30 seconds), logging "Host inbox registration failed; retrying in the background" on each failure. Routing configuration-validation failures still stop startup. An unavailable source or later observation failure needs operational investigation. Removing a source does not automatically delete its durable subscription or inbox history. Inventory and drain its cursor, then remove a subscription only through an approved operator procedure. At startup Ante creates Mongo indexes for accepted-invitation sessions; exchange depends on MongoDB. A 400 from `/_invite/exchange` can mean malformed/missing bearer token, malformed GUID `jti` or expired/missing `exp`; it does not establish the reason the proxy accepted or rejected a request. Inspect proxy verification and access controls as described in [Security and trust](./security.md). A failed optional `/in-use` HTTP call can allow join acceptance to proceed; the host's own uniqueness rule must hold. Review [Security](./security.md) before diagnosing untrusted identity headers in production.
