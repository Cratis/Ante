:::danger[Protect the forwarded identity]
Ante verifies RS256 invitation JWT signatures, lifetime, and configured issuer and audience before `POST /_invite/exchange` records a session. This does not authenticate the forwarded sign-in identity or the `jti` claim on later requests. Only a trusted proxy may reach Ante; it must strip untrusted identity headers and verify invitation claims before forwarding them. The repository does not establish that any deployment has this boundary correctly configured.
:::

## Token and identity boundaries

Ante issues RS256 JWTs with `jti` (the host-minted GUID invitation id), `invite_type` (`JoinTenant` or `CreateTenant`), issued time and expiry (seven days by default). Ante does not explicitly set `NotBefore` (`nbf`) on its token descriptor; if the JWT handler emits `nbf` by default, verifiers must honor it. At exchange Ante requires an expiration and validates the signature against the public key derived from its signing private key plus `PublicKeyPem` when configured. Only RS256 is accepted. Ante validates `iss` and `aud` against configured values; nonempty issuer and audience are mandatory outside Development, while Development may leave them empty and skip those checks. A 30-second clock skew applies during lifetime validation, but a session always ends at the signed `exp` without extension. Keep the private key secret, and coordinate external verifiers' signature, issuer, audience and lifetime policies.

After authentication the proxy is expected to POST the bearer invitation token and subject/provider details to the exchange. Ante stores the request body's `Subject` as sent, resolves the provider, and upserts a MongoDB session keyed by **subject plus provider**. Exchanging a second invitation for the same login replaces the first session. Exchange does not check that the invitation exists, is pending, or has not been revoked. Session expiry is copied from the validated token and checked when reading it; MongoDB's TTL index is only cleanup. The invitation-bound command validators call `IsVerifiedOwnerOf`: a matching `jti` on the forwarded principal is accepted directly, or a request's **subject and resolved provider** can match a live session for that invitation. Without an unambiguous request provider, the session path fails closed. The forwarded-`jti` path does not independently validate the JWT cryptography ([#13](https://github.com/Cratis/Ante/issues/13)); the exchange session path uses a validated token.

The proxy must strip or overwrite untrusted forwarded claims `jti`, `invite_type`, `iss`, `urn:cratis:identity:subject`, `urn:cratis:identity:provider-key`, `urn:cratis:identity:issuer`, `NameIdentifier` and `sub`. It must also control `x-ms-client-principal` (which carries the whole forwarded principal and its trusted claims), `x-ms-client-principal-id` and `x-ms-client-principal-name` (Arc's identity-id and identity-name headers), and, for registration email, the `email`, `upn`, `preferred_username`, `Name`, `ClaimTypes.Email` and `ClaimTypes.Upn` claims. Do not let a browser set these as trusted identity. Published `IdentityProvider` comes from the `iss` or canonical provider claims resolved against configured providers. Self-service `RegisterOrganization` has no invitation-owner check but rejects a missing signed-in subject; it derives email from forwarded sign-in values, and absent a plausible email the published field can be empty.

The browser decodes the URL token only to select a wizard. That decoding is not verification. For the exact exchange request see [Contracts](./contracts.md#http-surface).

## Generated API exposure

No endpoint in `Source/Ante` is marked `[Authorize]`. Restrict the whole `/api` surface at the proxy: other generated endpoints still depend on that boundary. The two instance-wide pending-invitation list queries are removed. The replacement queries return only the current invitee's pending invitation, and invitation-status and host-outcome queries check `IsVerifiedOwnerOf` before revealing state. Self-service registration uses a separate snapshot status query: a local, non-published owner event records subject and provider, and only a login matching **both** sees status or organization name. A local one-use event-source constraint blocks a second registration or an invited acceptance on the same id once any of those flows has claimed it. Command-side reads also reject pending invitations and older registrations or acceptances that predate this shared claim event; the append-time constraint is the concurrency-safe backstop for new attempts. An anonymous or different caller sees the same Pending/empty-name response as an unknown id. Registrations from before owner recording have no verifiable owner and also appear unknown; those users cannot resume their earlier registration via status polling. The browser rechecks the snapshot until durable ownership and publication become visible.

## Revocation and rotation

A host revokes by publishing `InvitationRevoked` under the original event source id. Ante removes the pending projection; invitation commands then reject a missing pending invitation once it has caught up. Revocation does **not** invalidate the JWT or an existing MongoDB exchange session at exchange time. An already issued link may still be parsed by the frontend. Do not promise immediate token invalidation.

Ante accepts the public key derived from its current signing private key and one optional additional `PublicKeyPem` verification key. To rotate, retain the outgoing key as `PublicKeyPem` while outstanding invitations expire, and coordinate the same overlap with the proxy and host. There is no general multi-key registry; replacing the only trusted key can invalidate outstanding links. The broader trust/protocol work is tracked in [Ante #11](https://github.com/Cratis/Ante/issues/11) and [verified ownership in #13](https://github.com/Cratis/Ante/issues/13).
