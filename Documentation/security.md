:::danger[Protect the forwarded identity]
Ante verifies RS256 invitation JWT signatures, lifetime, and configured issuer and audience at exchange (fixed in [Ante #51](https://github.com/Cratis/Ante/issues/51)). In Attested mode it separately verifies AuthProxy's signed stage and completion assertions. Neither mode verifies the forwarded sign-in principal on subsequent requests: only a trusted proxy may reach Ante, must strip untrusted identity headers, and must supply the canonical actor consistently. The repository does not establish that any deployment has this boundary correctly configured.
:::

## Choose an exchange mode

Choose `Legacy` only while your proxy and existing links still use the released capability-bearer exchange. It accepts a forwarded `jti` as invitation ownership and does **not** authenticate the body-supplied actor at exchange. Choose `Attested` for new recipient-bound links when AuthProxy is configured to sign staged exchanges and forward the **same** canonical provider key, authority and case-preserved subject on later requests. There is no fallback between modes. See [Configuration](./configuration.md#invitation-exchange-anteinvitationsexchange) and the [upgrade procedure](./deployment.md#switch-an-invitation-proxy-to-attested-mode).

## Token and identity boundaries

Ante issues RS256 JWTs with `jti` (the host-minted GUID invitation id), `invite_type` (`JoinTenant` or `CreateTenant`), issued time and expiry (seven days by default). In Attested mode, newly issued JWTs also carry `email` copied from the host invitation and `tenant_id` from `Ante:Invitations:Exchange:Attestation:LobbyScope`, never from the invitation's destination tenant name. Legacy mode does not add either claim. The email makes these JWTs both bearer secrets and personal data; do not expose them in logs, URLs beyond the necessary invitation link, or diagnostic payloads. Ante does not explicitly set `NotBefore` (`nbf`) on its token descriptor; if the JWT handler emits `nbf` by default, verifiers must honor it. At exchange Ante requires an expiration and validates the signature against the public key derived from its signing private key plus `PublicKeyPem` when configured. With no private key, Ante starts with a warning but rejects every exchange, even when the additional public key is present; issuance still cannot sign. A mandatory startup key is tracked for the next major release in [Ante #69](https://github.com/Cratis/Ante/issues/69). Only RS256 is accepted. Ante validates `iss` and `aud` when configured; empty values skip the corresponding check and produce startup warnings outside Development (making them mandatory is tracked for the next major release in [Ante #69](https://github.com/Cratis/Ante/issues/69)). A 30-second clock skew applies during lifetime validation, but a session always ends at the signed `exp` without extension. Keep the private key secret, and coordinate external verifiers' signature, issuer, audience and lifetime policies.

In Legacy mode, after authentication the proxy POSTs the bearer invitation token and subject/provider details to the exchange. Ante rejects a missing/blank subject or unresolved provider; otherwise it stores the request body's `Subject` as sent, resolves the provider, and upserts a MongoDB session keyed by **subject plus provider**. Exchanging a second invitation for the same login replaces the first session. Exchange does not check that the invitation exists, is pending, or has not been revoked. Session expiry is copied from the validated token and checked when reading it; MongoDB's TTL index is only cleanup. The invitation-bound command validators call `IsVerifiedOwnerOf`: a matching `jti` on the forwarded principal is accepted directly, or a request's **subject and resolved provider** can match a live session for that invitation. Without an unambiguous request provider, the session path fails closed. Ante uses one provider-candidate rule for both the exchange body and later forwarded requests. AuthProxy's legacy exchange body selects **one** value: `iss`, then `identity_provider`, then the Microsoft access-control-service identity-provider claim, then the principal's `AuthenticationType`. Later requests carry the raw claims and Arc's provider metadata (from `AuthenticationType`); Ante makes the same single selection, not a list of fallback legacy claims. When AuthProxy resolves canonical identity, exchange sends `providerKey`, normalized `issuer`, and `identityProvider` equal to the key; later requests carry `urn:cratis:identity:provider-key` and `urn:cratis:identity:issuer` plus Arc's key metadata. Ante considers only the canonical key and issuer in this mode, never legacy claims or accepted-session fallback as a substitute for a canonical key/issuer that is not configured. If nothing identifies the provider, Ante infers one only when exactly one provider is configured; a bare `AuthenticationTypes.Federation` marker requires that sole provider to have an issuer. Multiple providers, including a mixed issuerless/OIDC deployment, require an identifying signal at exchange or the request's session path fails closed. An unresolved exchange provider is rejected with a warning that contains no account or token values. The forwarded-`jti` path does not independently validate the JWT cryptography in Legacy mode; the exchange session path uses a validated token. In Attested mode, `jti` is only a hint for finding a session, not authorization. The stage assertion must bind the independently verified capability to the transaction, challenge, invitation id, lobby scope, recipient and flow. Completion requires a fresh, purpose-specific signed assertion with approved assurance, authentication time, canonical provider key/authority/subject, verified matching email and that same stage binding. A single MongoDB document atomically records the completed transaction, assertion replay IDs and actor-bound session; retries cannot extend expiry. Subsequent commands, owner-checked reads and `/.cratis/me` require an unexpired session for the exact lobby scope, invitation id, provider key, authority and **case-sensitive canonical subject** forwarded by AuthProxy. A legacy session, an unqualified subject or a forwarded `jti` without an attested session grants no ownership. Self-registration is independent of invitation staging.

Arc's Microsoft identity platform handler decodes the request principal from the `x-ms-client-principal` header, with `x-ms-client-principal-id` and `x-ms-client-principal-name` alongside it. The proxy must strip any client-supplied copy of all three headers and set them itself. Inside that principal, Ante trusts `jti`, `invite_type`, `iss`, `urn:cratis:identity:subject`, `urn:cratis:identity:provider-key`, `urn:cratis:identity:issuer`, `identity_provider`, `http://schemas.microsoft.com/accesscontrolservice/2010/07/claims/identityprovider`, `urn:cratis:arc:identity:provider`, `NameIdentifier` and `sub`; a spoofed `iss` can change the published `IdentityProvider` key. Registration email also uses the `email`, `upn`, `preferred_username`, `Name`, `ClaimTypes.Email` and `ClaimTypes.Upn` claims. Do not let a browser set these as trusted identity. Self-service `RegisterOrganization` has no invitation-owner check but rejects a missing signed-in subject or unresolved provider; absent a plausible email, the published field can be empty.

The browser chooses the wizard from identity details first and falls back to the URL token's unverified `invite_type`; when a token is present, it also uses the token's unverified `jti` as the invitation id it submits and polls. Neither is verification: invitation commands are gated server-side by `IsVerifiedOwnerOf`. For the exact exchange request see [Contracts](./contracts.md#http-surface).

## Personal data, retention and erasure

The host sets retention deadlines and legal holds; Ante must remove its own copies when an approved erasure is due. Do not infer the encryption-key subject from an invitation id: received events preserve the host's compliance subject, while later facts can use the signed-in actor's subject. Inventory subjects and stores for each operation before deleting anything.

| Data class | What Ante retains | Classification in current source |
| --- | --- | --- |
| Pending invitations | Host-supplied email, tenant name and roles in inbox/local receipt and pending read models; revocation removes the pending projection, not necessarily event history. | `Email` is `[PII]`; `TenantName` and `RoleName` are not. Names and roles can still be identifying in context. |
| Staged transactions (Attested only) | MongoDB `StagedInvitationTransaction` holds scope, invitation, flow, capability hash, independent challenge, recipient email and expiry no later than 15 minutes or capability expiry; never the raw capability. Mongo TTL is cleanup, not authorization. | The recipient email is personal data in MongoDB; Chronicle's event annotation does not encrypt this copy. Restrict access and include it in erasure procedures. |
| Exchange sessions | Legacy MongoDB `AcceptedInvitation` holds subject, provider, invitation id, flow and exchange/expiry times. Attested mode stores the scope, invitation, provider key/issuer/subject, expiry and replay assertion IDs in `AttestedInvitationSession`; it is the completion record, not an adjunct to a consumed marker. TTL indexes only clean up eventually; both paths check expiry at use. | Mongo session fields have no `[PII]` annotation. Subject/provider pairs remain personal data even without one. |
| Acceptance and legal facts | Invited acceptance and self-registration carry identity subjects, names, email and tenant context; optional `LegalTermsAccepted` carries provider, raw identity-provider subject and document version. Facts are copied to Ante's outbox and can reach host inboxes. | `Email`, `FirstName`, `MiddleName` and `LastName` concepts are `[PII]`. Raw subject strings in published acceptance/registration/legal contracts and tenant/provider/role concepts are not `[PII]`-annotated; classification is not a guarantee that other data is anonymous. |
| Registration owner | Local `RegistrationOwnerRecorded` stores a subject and provider for status authorization; it is not forwarded to the host. | `RegistrationOwnerSubject` is `[PII]`; provider is not. |
| Invitation tokens | `InvitationTokenIssued` in Ante's outbox contains the signed JWT and expiry; the host receives it to build the link. Legacy tokens have invitation id and flow; Attested-mode tokens also carry the invited email and lobby scope. | Generation-3 `Token` is property-level `[PII]`-classified. Generation-1/2 tokens were unannotated, and schema migration cannot retrospectively encrypt their plaintext. Protect all generations as bearer secrets; token publication is not email delivery. |

**Proposed operational defaults, not statutory periods or implemented automatic cleanup:** host-scheduled pending-invitation erasure 30 days after expiry/revocation; completed onboarding PII 90 days after terminal outcome (or publication when host feedback is disabled); minimal pseudonymous operational traces for one year, subject to linkability review. Exchange sessions stop authorizing at signed expiry; MongoDB's TTL cleanup is not instantaneous, so plan cleanup and earlier removal on subject erasure. Retain legal evidence only under the host's approved legal retention and hold policy, with no universal Ante period. The host must supply actual deadlines and holds; Ante cannot infer when an invitation was last sent from token issuance.

Chronicle 19.4.7's cross-store subscriber copies a compliance subject's encryption key to a target store/namespace when absent. Erasing the key in the host does **not** erase Ante's copy. Forwarding can recreate a deleted copy **if deletion has not installed an effective erasure fence**; that subscriber checks a target erasure record with `NewKeyAllowed: false` and its key storage refuses prohibited writes. Account for every copy and the fence's behavior, not just one store. `[PII]` annotations do not retroactively erase older plaintext or protect raw identity strings; include host link storage, logs, exports, backups and restores in the policy.

:::caution[Complete automated erasure is not available]
Ante has no automated end-to-end erasure workflow or completion acknowledgement. Do not claim completion from a single key deletion. Rehearse the [quiesced manual erasure procedure](./operations.md#rehearse-a-quiesced-erasure) before use; resurrection-safe automation is tracked in [Ante #64](https://github.com/Cratis/Ante/issues/64).
:::

## Generated API exposure

No endpoint in `Source/Ante` is marked `[Authorize]`. Restrict the whole `/api` surface at the proxy: other generated endpoints still depend on that boundary. The two instance-wide pending-invitation list queries are removed. The replacement queries return only the current invitee's pending invitation, and invitation-status and host-outcome queries check `IsVerifiedOwnerOf` before revealing state. Self-service registration uses a separate snapshot status query: a local, non-published owner event records subject and provider, and only a login matching **both** sees status or organization name. A local one-use event-source constraint blocks a second registration or an invited acceptance on the same id once any of those flows has claimed it. Command-side reads also reject pending invitations and older registrations or acceptances that predate this shared claim event; the append-time constraint is the concurrency-safe backstop for new attempts. An anonymous or different caller sees the same Pending/empty-name response as an unknown id. Registrations from before owner recording have no verifiable owner and also appear unknown; those users cannot resume their earlier registration via status polling. The browser rechecks the snapshot until durable ownership and publication become visible. A one-use rejection after retrying a registration (for example, after a lost submit response) resumes bounded status polling rather than treating the retry as a fresh operation; unrelated validation failures do not.

## Revocation and rotation

A host revokes by publishing `InvitationRevoked` under the original event source id. Ante records revocation locally and removes the pending projection. Attested stage and new completion check the authoritative local log; both invitation acceptance commands also read that log and append under a concurrency scope that includes revocation, so an intervening locally appended revocation rejects the acceptance batch. Delivery from the host to Ante is asynchronous: a revocation not yet received locally cannot be enforced by Ante. Legacy exchange does **not** invalidate a JWT or an existing MongoDB session at exchange time; committed attested completion retries do not reauthorize a revoked invitation. An already issued link may still be parsed by the frontend. Do not promise immediate token invalidation.

Ante accepts the public key derived from its current signing private key and one optional additional `PublicKeyPem` verification key. To rotate, retain the outgoing key as `PublicKeyPem` while outstanding invitations expire, and coordinate the same overlap with the proxy and host. There is no general multi-key registry; replacing the only trusted key can invalidate outstanding links. The broader trust/protocol work is tracked in [Ante #11](https://github.com/Cratis/Ante/issues/11) and [verified ownership in #13](https://github.com/Cratis/Ante/issues/13).
