---
title: Integrate a host product
description: Connect host invitation events, token links, provisioning, and the required proxy to Ante.
---

A host owns the invitation decision, link delivery, identity configuration and provisioning. Ante handles token issuance and lobby acceptance. Set `Ante:HostStores` to the host's actual Chronicle source stores, for example `["Direct"]` or Studio's `["Studio", "StudioAdmin"]`. Ante defaults to `["Direct"]` if neither source setting is supplied. This no longer requires rebuilding Ante. See [Configuration](./configuration.md).

## Connect the event stores

1. Mint a nonempty GUID invitation id, serialize it as lowercase hyphenated `D` format, and append `UserInvitedToJoinTenant` or `UserInvitedToCreateTenant` to **your host store's outbox**, using that GUID as the event source id. **Use a fresh invitation id for every distinct invite, including after revocation or acceptance.** In Attested mode, ids are single-use even while pending: a different event under an existing id produces `InvitationRejected(InvitationIdReused)` instead of another receipt or token. An identical redelivery from the same host source while pending produces neither a second receipt nor a token. Legacy mode still permits a different event for a pending id, so use a fresh id for each invite in either mode. Revocation appends `InvitationRevoked` under the same id. An ordinary host event-log append is not the cross-store outbox input Ante observes. The exact fields and namespaces are in [Contracts](./contracts.md).
2. Observe Ante's outbox for `InvitationTokenIssued` **and** `InvitationRejected`. For a rejection with `Reason = InvalidInvitationId`, correct the host's noncanonical event source id and issue a new invitation. For `Reason = InvitationIdReused`, mint a new id and issue a new invitation instead of resending under the old id. In Attested mode, `InvalidRecipient` means the host email cannot be bound into a token: correct it and issue a new invitation id. A rejection does not issue a token; invalid recipients can leave a locally recorded receipt, so hosts should replace the invitation with a new id. Chronicle's outbox-to-inbox forwarder may copy the same host event again under a new inbox sequence number, which can produce `InvitationIdReused` after an id is closed; ignore rejections for ids already revoked or accepted. **Deduplicate both `InvitationRejected` and `InvitationTokenIssued`:** Ante publishes them from reactors that also run on replay and redelivery, so the same outcome can reach your host more than once. Deduplicate per invitation id and event type. Ante concludes each receipt and each reissue request with one outcome: a redelivery or replay publishes an outcome only when the outbox has none for that receipt or request yet, while each reissue request gets a **new** token. An invitation that waited for a signing key gets its token when an instance with a key resumes it, and none if it was revoked while waiting. Outcomes published by earlier versions of Ante could repeat with a fresh JWT, and the forwarder can still copy an outcome again, so a later `InvitationTokenIssued` for the same id should replace the one you hold, for example by keeping the token with the latest `ExpiresAt`, not trigger another invitation message.
3. For a token, build the link as `/invite/{token}` on the **proxy's** public origin and distribute it using your own channel. Cratis AuthProxy handles that path itself: it validates the token's signature and lifetime, and its issuer and audience when those are configured on both AuthProxy and Ante (`Ante:Invitations:Token:Issuer`/`Audience`; see [Security and trust](./security.md)), runs sign-in and the exchange, then redirects to its configured lobby frontend URL (`Cratis:AuthProxy:Invite:Lobby:Frontend:BaseUrl`). If a request for `/invite/{token}` reaches Ante directly, Ante serves the lobby shell for it as well. Treat tokens as secrets; Ante does not send mail. Generation 3 carries `ExpiresAt`, the UTC JWT `exp` instant and classifies the token as PII (generation 2 also carries `ExpiresAt`); generation-1 facts migrated for new consumers use `DateTimeOffset.UnixEpoch` because their historical expiry is unknown. Do not announce or send a link for a token whose expiry is unknown or past. Multiple token-issued events for an id are possible. Check that a token arrives before announcing the link as usable.
4. Consume `InvitationToJoinTenantAccepted`, `InvitationToCreateTenantAccepted`, `OrganizationRegistrationCompleted` and, if legal documents are configured, `LegalTermsAccepted`. Make provisioning idempotent by event source id and event kind. The acceptance is evidence from Ante; enforce membership, role, identity-association and tenant uniqueness in your host. `Accepted` in Ante means published to its outbox, not provisioned in your system.

**Host upgrade:** consume generation-3 `InvitationTokenIssued` **before** Ante starts publishing it: Chronicle cross-store subscriptions do not downcast the new generation for an old host. Keep the link and its embedded recipient email private. Add `InvitationRejected` generation 2 and its `InvitationIdReused` and `InvalidRecipient` reasons to the event types your host observes from Ante's outbox (and to mirrored contract definitions, if used). A host that observes only `InvitationTokenIssued` will not receive rejection events. On Chronicle 19.22.1 the isolated generation-2-only host reads a usable JWT, but **its raw MongoDB `inbox-{ante store}` generation-3 token is plaintext**, unlike the encrypted generation-3 token in Ante's outbox and the current host inbox. The older typed read does not establish a safe upgrade path or retroactive encryption; upgrade the consumer's PII metadata and protect existing token storage and backups. Hosts still using a generation-1 token-issued mirror must tolerate the additional `expiresAt` JSON member in cross-store deliveries.

Use the [`Cratis.Ante.Contracts` NuGet package](https://www.nuget.org/packages/Cratis.Ante.Contracts) for the public event types. CI packs it with the image's release version when publishing is approved. The package still has an assembly-level `[EventStore("Ante")]`. A host can *already reference it* with any Ante store name: explicitly annotate its observer with `[EventStore("DirectLobby")]` (replace `DirectLobby` with the actual Ante store). That observer-level setting wins over the assembly annotation. Removing the assembly annotation is deferred to a coordinated breaking contracts release; existing observers may rely on the default. Do not duplicate discovered CLR event types with the same identities when replacing mirrors. If you keep mirrored contracts (as Direct currently does), compare event ids, generations, serialization and `[PII]` metadata; matching names alone do not establish compatibility.

Ante resolves one fixed namespace (`Ante:Namespace`, default `Default`) across all its requests and subscriptions. Chronicle forwards each host outbox into `inbox-{source}` in that *same namespace* on Ante's store; there is no namespace remapping. Publish and observe in a matching namespace, and test the full path before cutover. The host observer of Ante's outbox must likewise follow Ante's configured store and matching namespace. A multi-source list grants the three invitation contract types to each configured store; Inbox mode also subscribes its one configured legal publisher store to `LegalDocumentSetPublished`. The list does **not** enforce flow-specific Core/Admin permissions. These stores must belong to one trusted host product. The three inbound contracts currently use generation 1; Chronicle's subscription builder emits generation-1 filters, so a future inbound event generation needs a coordinated adapter change. Studio's Core revocation `UserInvitationRevoked` differs from Ante's `InvitationRevoked` and needs producer-side adaptation. The [Architecture](./architecture.md) page separates each host outbox, Ante inbox and Ante outbox.

For an invited event, Ante copies the host event context's compliance `Subject` into the local receipt, and the pending invitation read model projects it as a `Guid`. On join, `SignedInIdentity.Resolve` can fall back to that subject if the request/session has none. Supply the host event with a valid compliance subject and verify projection and identity behavior in an integration test; this repository does not establish what a missing or non-GUID subject does across the cross-store boundary. `IdentityProviderSubject` in the published acceptance payload is a plain string so the host can use the signed-in subject as a user key rather than infer it from compliance metadata.

A source-checked **illustrative excerpt**, not a standalone compilable host program (the surrounding host store, typed concepts and registration are omitted), shows the append shape used by Ante's own `InvitationTokenIssuingReactor`:

```csharp
await eventStore.GetEventSequence(EventSequenceId.Outbox)
    .Append(invitationId.ToString(), new UserInvitedToJoinTenant(email, tenantName, roles));
```

Here `invitationId` is a `Guid`, `email` is `Email`, `tenantName` is `TenantName`, and `roles` is `IReadOnlyList<RoleName>`. Ensure the `eventStore` points to the host store, not Ante's. A complete host fixture with compiling setup and end-to-end tests is not included in this repository. Direct is one host implementation, but its current source does not prove a working invitation end to end; do not copy its id generation without checking the GUID requirement. For a host that needs runtime-configurable reverse routing rather than a compiled `[EventStore]` observer, use Chronicle's runtime reactor on `inbox-{configured Ante store}` and a single subscription from that store's outbox, filtering the union of events its host consumers need. Coordinate ownership of the source-name subscription id: separate consumers must not overwrite one another's filters. Neither adapter nor event-type filtering can route a token to only one of Studio's stores; each consumer must correlate the invitation id and ignore unrelated ids.

## Put a verifying proxy in front

Do not expose Ante directly. For the released **Legacy** exchange only, validate the invitation at the proxy before forwarding its `jti` and `invite_type` claims; Ante independently verifies the bearer invitation token at exchange (RS256, lifetime, and configured issuer/audience) according to [Security and trust](./security.md). Then call `POST /_invite/exchange` after sign-in with `Authorization: Bearer <invite-token>` and this **camelCase** JSON body (values are illustrative; substitute the signed-in identity):

```json
{
  "subject": "signed-in-subject",
  "identityProvider": "issuer-or-provider-name",
  "providerKey": "canonical-provider-key",
  "issuer": "canonical-issuer"
}
```

`providerKey` and `issuer` are optional; provider resolution tries `ProviderKey`, then `Issuer`, then `IdentityProvider`, and resolves a recognized configured provider name before retaining an unknown report. With no provider information at all, Ante falls back only when exactly one provider is configured. A bare `AuthenticationTypes.Federation` marker falls back only when exactly one provider is configured **and it has an issuer**; a mixed OIDC/OAuth2 deployment cannot infer a provider from that marker or from silence and returns 400. Unknown explicit provider names are retained as reported. The proxy's invitation-claims forwarding must supply verified `jti` and `invite_type` to the principal for request-time invitation resolution. If configured to resolve a canonical federated identity, it can also forward `urn:cratis:identity:subject`, `urn:cratis:identity:provider-key`, and `urn:cratis:identity:issuer`; Ante prefers these when resolving subject and provider. Without canonical provider claims or `iss`, Ante also uses Arc's `urn:cratis:arc:identity:provider` claim (authored from the trusted principal's `identityProvider` field), before considering any fallback. Ensure it identifies the same provider as the exchange request. The exchange session is a fallback when the invitation claims are not forwarded, but ownership requires the forwarded sign-in subject **and an unambiguous resolved provider** to match the stored session. A subject alone never proves ownership across providers. Keep the proxy's provider-key/issuer claims consistent across exchange and subsequent requests. Strip or overwrite all identity/claim inputs detailed in [Security and trust](./security.md). This repository specifies Ante's expectations, **not** a tested AuthProxy setup.

### Enable staged, attested invitation exchange

For new recipient-bound invitations configure both AuthProxy and Ante for the signed protocol. This is a separate opt-in deployment, not a fallback from an attestation failure. Set the proxy's `Cratis:AuthProxy:Invite:StageUrl` to Ante's private `/_invite/stage` URL and `ExchangeUrl` to its private `/_invite/exchange` URL. Set `TenantClaim=tenant_id`, `EmailClaim=email` and `MatchingTenantInvitationDestination=Lobby` so matching-tenant invitations still reach Ante's wizard rather than the host ReturnUrl. Set `Lobby:Frontend:BaseUrl` to the public Ante lobby. The `tenant_id` must match Ante's configured `Attestation:LobbyScope` and AuthProxy's resolved authentication tenant, **not** the invited organization name or a membership grant.

Enable `Cratis:AuthProxy:Invite:Attestation` with exact `Issuer`, `Audience`, `ActiveKeyId`, 10–60-second `Lifetime` and `SigningKeys` containing the private RSA key loaded from a secret provider. Set Ante's `Ante:Invitations:Exchange:Mode=Attested`, matching attestation issuer/audience/scope, pinned `PublicKeys` (`KeyId`, **public** PEM) and `Providers` (`Key`, `Issuer`, `AcceptableAssurances`). Never place the proxy's private signing key in Ante. Pin new public keys before switching AuthProxy's active key, and keep old pins until old assertions expire. The separate Ante capability-signing key and AuthProxy invitation-verification key also need coordinated rotation.

For each provider, AuthProxy must send canonical provider key, validated issuer, case-preserved subject, provider-derived verified email and an approved assurance value and authentication time in the signed completion. Configure `CanonicalIdentity.InvitationCompletionEnabled=true` only for providers that actually emit these facts; do not infer `email_verified` from an address-shaped username. Forward `urn:cratis:identity:subject`, `urn:cratis:identity:provider-key` and `urn:cratis:identity:issuer` from the **same** login on subsequent commands, queries and `/.cratis/me`; stripping client-authored identity headers remains mandatory. Host code must consume the generation-3 token event and verify both join and create invitations use its new `email` and `tenant_id` JWT claims. Recipients bound to an immutable provider HMAC are not supported by this Ante mode.

Direct needs a deployment/proxy configuration update, public-key pinning and a checked generation-3 token consumer; verify its GitHub provider actually supplies verified email and assurance before enabling it. Studio is not yet an Ante consumer: replace its local Admin/Core token signing with Ante issuance, adapt contract generations and store routing, then configure the same proxy and acceptance handling. Neither host change is made by this repository; do not advertise live AuthProxy/Direct/Studio interoperability until it is tested. See the [cutover plan](./deployment.md#switch-an-invitation-proxy-to-attested-mode) and [sequence](./invitation-lifecycle.md).

For self-service onboarding, direct users to `{public-lobby-url}/register` and authenticate them through the proxy without inventing an invitation token. Ensure trusted sign-in claims include a stable subject and provider for owner-verified registration status. `OrganizationRegistrationCompleted.Email` may be empty; when present it is only an address-shaped contact candidate from forwarded claims, not verified mailbox ownership, identity, or permission to merge accounts. If your provisioning needs a verified contact, collect and verify it there rather than requiring Ante's self-registration wizard to establish it. Ante records registration ownership in a local event, never the host outbox. Older registrations without that event appear unknown to the status query and cannot be resumed through status polling. See [Contracts](./contracts.md#http-surface) for exact endpoints.

## Add optional host reads

For join invitations, `Ante:IdentityBackchannelUrl` adds a GET to `/in-use?organization=...&subject=...` before acceptance. It is fail-open for network/timeouts/JSON errors, so your host must enforce uniqueness itself. `Ante:HostOutcomeUrl` adds a GET to `/outcome?attempt=...` after publication for invited journeys and self-service registration (for registration, `attempt` is the registration id and only the sign-in recorded as its owner sees the answer). Its status is informational and a failed/unknown response never reverses Ante's publication. Protect these endpoints and their query-string data at the network and logging boundaries. Neither adapter supplies its own application-level authentication credential. Their outage warnings log the exception, not the organization name or subject; protect access to exception logs and HTTP access logs separately. Their exact JSON shapes are in [Contracts](./contracts.md#http-surface).

## Publish legal documents from a separate host

1. Set `Ante:Legal:Source=Inbox`, `Ante:Legal:PublisherStore` to **one** of Ante's configured `HostStores`, and `Ante:Legal:DocumentSetId` to a stable non-GUID id (for example `legal-documents-main`). Use that exact event-source id for every publication on the publisher's outbox. Its namespace must match Ante's fixed `Ante:Namespace`. Restrict writes to the host outbox and its Chronicle credentials to authorized legal publishers; naming a store in Ante is routing, not authentication of arbitrary writers to that store.
2. Start Ante in Inbox mode **before** publishing. Confirm the subscription from the configured publisher store's outbox to Ante includes `LegalDocumentSetPublished` alongside its invitation filters. Ante's runtime inbox reactor shares the source-qualified invitation observer and subscription id; **merge**, do not replace, those filters. In Chronicle 19.13.1, adding the legal type to an existing subscription does not backfill earlier outbox publications of that type.
3. Subscribe your host store to Ante's outbox for `LegalDocumentSetActivated` alongside its existing filters; handle acknowledgements idempotently. Then publish `new LegalDocumentSetPublished(revision, version, fullTerms, fullPrivacy)` on the host **outbox** (not merely its event log). Use a positive, monotonically increasing `LegalDocumentRevision`, a `LegalVersion` owned by the host, and the complete two bodies each time. Archive each version with the exact bodies for consent audit. Do not reuse a revision or a version for different content. Wait for the acknowledgement for that revision before treating it as available to invitees. If no set is active after confirming the legal filter, republish the current set: an identical republish is a harmless no-op when it was already activated. An asynchronous publication is not an instantaneous global switch. Until the first set activates, Ante blocks all three onboarding submissions rather than skipping consent. Ante also rejects an acceptance if activation races its command append; the invitee must reload the current set.

For an embedded host, the default remains `InProcess`: register `ILegalDocumentSource` **inside the Ante process**, through a custom composition of `Program.cs`; registering it in a separate host's DI container cannot affect Ante. Stock startup installs `NoLegalDocumentSource` and shows no legal step. See [Customization](./customization.md) and [Contracts](./contracts.md).

## Resend an invitation

To send an invitee a fresh link - they lost the email, or the link expired - append `InvitationReissueRequested` to your outbox under the **same** invitation id. Ante answers with a new `InvitationTokenIssued` carrying its own `ExpiresAt` while the invitation is pending, or with `InvitationRejected(InvitationNotPending)` when it was never received, was revoked or was accepted; in that case create a new invitation with a new id. A redelivered request is answered once. Earlier tokens stay valid until they expire: revoke and re-invite with a new id when an earlier link must stop working. Keep only the latest `ExpiresAt` per invitation, and never email a token whose expiry has passed.

## Keep organization names in step with the host

Ante refuses an organization name, ignoring case, that is claimed by an earlier invited creation or registration, reserved by the host, or listed in `Ante:Organization:ReservedNames`. Before routing onboarding traffic to Ante, publish `OrganizationNameReserved` for every organization the host already has, so a new registration cannot collide with an existing tenant. When the host deletes an organization and its name may be used again, publish `OrganizationNameReleased`; Ante releases every claim it holds for that name. Both events are received from any `Ante:HostStores` source. The host's own uniqueness rule stays authoritative: Ante's registry prevents the obvious collision early, it does not replace the check during provisioning.

## Offer self-service signup

`/register` is on by default; set `Ante:Registration:Enabled=false` on a deployment that should only onboard invited people, and use it as a kill switch during abuse. For a public signup link (for example a "Start free trial" button on a marketing site):

- List the query-string keys you want back in `Ante:Registration:ContextKeys` (for example `offer`, `utm_source`, `utm_medium`, `utm_campaign`) and link to `https://<lobby>/register?offer=trial&utm_source=site`. The keys arrive as `OrganizationRegistrationCompleted.SignupContext`. Make sure the fronting proxy preserves the query across the external sign-in redirect; Ante also keeps it for the tab once seen.
- Describe the offer with `Ante:Registration:Content:{locale}` (see [Customization](./customization.md#describe-the-registration-offer)).
- Bound abuse with `Ante:Registration:MaxPerIdentity`/`Window` and `RequestsPerMinutePerClient` (see [Security and trust](./security.md#self-service-registration-limits)).
- Configure `Ante:HostOutcomeUrl` so the new owner waits on a completion screen until your provisioning succeeds, instead of arriving before the organization exists.
